Deployment    Docker multi-stage image (Next standalone), Docker Compose, nginx
Tooling       bun (package manager), Node >= 20.9 runtime, ESLint 9, Biome 1.9, knip

============================================================
3. MODULE BOUNDARIES (src/modules/<module>)
============================================================

identity       authentication, session validation, permissions (admin role, guards)
merchants      onboarding, profiles, memberships, pickup/return addresses, approval status
catalog        products, categories, images, variants, publication status
inventory      available stock, reserved stock, adjustments, reservations, movements
cart           carts and cart items (multi-merchant)
checkout       quote, server-side price/stock/serviceability validation, order placement
orders         parent orders, merchant suborders, items, transitions, cancellation
payments       payment attempts, provider references, confirmation, refunds, COD state
fulfillment    packaging status, shipments, courier assignment, tracking history
finance        fee settings, commission/shipping snapshots, payables, remittances (no payouts)
reviews        verified reviews, ratings, merchant replies, moderation
notifications  new-order, dispatch, delivery, SLA alerts

Layers per module (only when needed): domain/ (pure rules, state machines),
application/ (use cases), infrastructure/ (Drizzle, provider adapters, jobs),
presentation/ (Zod DTOs, mappers), index.ts (public interface — other modules
import only this).

Cross-cutting: src/platform/ (env, logger, request id, errors, outbox,
idempotency, queue). Process entrypoints: src/workers/*.ts.

Rules:
- A module writes only its own tables; cross-module changes go through the
  owning module's public service or an outbox event.
- Merchant-scoped queries take merchantId from the authorized membership,
  never from the request body.
- Business rules never live in React components or route handlers.

============================================================
4. ROLES
============================================================

ADMIN     better-auth admin plugin, user.role contains "admin"; granted only by CLI (admin:grant)
CUSTOMER  any authenticated user
MERCHANT  membership row in merchant_members (owner | staff) on a merchant;
          selling capabilities additionally require merchant status APPROVED.
          One user may be a customer and a member of several merchants.

5. DATABASE DESIGN (tables by introducing phase)
============================================================

Conventions: text cuid2 primary keys; created_at/updated_at timestamptz;
explicit FK on-delete; money = integer paise in bigint with CHECK >= 0;
status columns = Postgres enums matching requirements §18; order numbers
GIL-<n> (parent) and GIL-<n>-<A|B|...> (merchant suborder) from a sequence.

Phase 1  user, session, account, verification, two_factor (+ admin plugin columns), uploads
Phase 2  merchants, merchant_members, merchant_pickup_locations
Phase 3  categories, products, product_variants, product_images, inventory, inventory_movements
Phase 4  carts, cart_items
Phase 5  customer_addresses, orders, merchant_orders, order_items, order_address_snapshots,
         order_status_history, inventory_reservations, idempotency_keys, outbox_events,
         background_job_attempts, merchant_fee_settings, merchant_payables
Phase 6  payment_attempts, payment_provider_events, refunds, provider_remittances
Phase 7  shipments, shipment_tracking_events, shipping_quotes
Phase 8  product_reviews, merchant_review_replies (+ notifications if needed)

Non-negotiable constraints (diagrams/core-entiies.txt): every product belongs
to a merchant; merchant members explicitly authorized; order item prices
snapshotted; inventory never negative; payment attempt maps to exactly one
order; provider ids unique; duplicate webhooks never cause duplicate
transitions; orders keep their shipping address snapshot.

Stock reservation: UPDATE inventory SET available = available - q,
reserved = reserved + q WHERE product_id = p AND available >= q
(zero rows => out of stock => rollback).

============================================================
6. DEPLOYMENT
============================================================

Compose services: gillu-postgres, gillu-redis, gillu-migrate (one-shot),
gillu-web, gillu-nginx (Phase 1); gillu-outbox-dispatcher (Phase 5),
gillu-payment-worker (Phase 6), gillu-shipping-worker (Phase 7).
Workers reuse the web image with a different command. Postgres and Redis
publish no ports. Secrets only via env files, never in images.
