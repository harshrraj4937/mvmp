# PROJECT GILLU — MULTI-VENDOR MARKETPLACE MVP

## ROLE

You are the principal software architect, senior full-stack engineer,
backend engineer, database engineer, DevOps engineer, and QA engineer
responsible for building Gillu.

Your task is to transform the existing Relivator starter repository into
a functional, tested, multi-vendor Indian e-commerce marketplace.

You must implement the project incrementally.

Do not attempt a complete rewrite.

Do not create disconnected mockup pages.

Do not implement everything in one enormous change.

Every phase must result in functioning, tested software.

============================================================
1. PROJECT CONTEXT
============================================================

PROJECT NAME:
Gillu

PROJECT TYPE:
Multi-vendor e-commerce marketplace for India.

STARTER REPOSITORY:
https://github.com/reliverse/relivator

EXISTING LANDING PAGE:
https://gillu-festive-haat.warmsiren2.chatgpt.site/

PAYMENT PROVIDER:
Cashfree

SHIPPING PROVIDER:
Shiprocket

SHIPROCKET SANDBOX:
https://sandbox.shiprocket.in/apis/

SHIPROCKET API DOCUMENTATION:
https://apidocs.shiprocket.in/

CASHFREE DOCUMENTATION:
https://www.cashfree.com/docs/

Gillu allows multiple independent merchants to sell products
through a common storefront.

The initial product categories focus on Indian traditional,
regional, cultural, and festive products.

The platform has three user interfaces:

1. Customer storefront
2. Merchant dashboard
3. Marketplace administration dashboard

A merchant can register, publish products, receive orders,
prepare packages, and manage shipments.

A customer can browse products from multiple merchants,
add products to a cart, provide an address, and purchase
using prepaid payments or Cash on Delivery.

Cashfree processes prepaid payments.

Shiprocket manages courier availability, shipment creation,
AWB generation, pickup requests, and shipping tracking.

Gillu owns the authoritative marketplace order records.

============================================================

Follow these principles:

1. Separation of concerns
2. Domain-driven module boundaries
3. Single responsibility principle
4. Dependency inversion
5. Explicit service interfaces
6. High cohesion within modules
7. Low coupling between modules
8. Server-side authorization
9. Database transaction safety
10. Idempotent external operations
11. Durable asynchronous events
12. Test-driven development for critical business logic
13. Observable error handling
14. Minimal necessary abstraction
15. Incremental delivery

Avoid overengineering.

Do not create microservices for every domain.

Do not add Kubernetes, Kafka, Elasticsearch, or other infrastructure
until a real requirement justifies them.

11. MULTI-MERCHANT ORDER MODEL
============================================================

Gillu supports multi-merchant carts.

A customer can add products from Merchant A and Merchant B
to the same cart.

At checkout:

1. Create one parent customer order.
2. Create one merchant-specific suborder per merchant.
3. Copy the correct items into each merchant suborder.
4. Store all price snapshots.
5. Reserve inventory.
6. Associate each merchant suborder with its seller.
7. Process the customer payment according to payment method.
8. Allow independent fulfillment of each merchant suborder.

Example:

Parent Order GIL-1001

Merchant Order GIL-1001-A
  Merchant: A
  Product: Cashews
  Quantity: 2

Merchant Order GIL-1001-B
  Merchant: B
  Product: Handicraft
  Quantity: 1

Each merchant sees only their own suborder.

Each merchant has independent shipping and tracking.

The customer sees the complete parent order.

13. SHIPPING-INCLUDING PRODUCT PRICING
============================================================

BUSINESS DECISION:

Gillu intends to include estimated delivery costs within
the customer-facing product selling price.

The goal is to present predictable all-inclusive pricing.

HOWEVER:

The final pricing formula and merchant unit economics
are intentionally deferred until after MVP validation
and interviews with real sellers.

Therefore:

- Store seller base price separately where applicable.
- Store advertised selling price.
- Store courier estimate.
- Store actual courier charge.
- Store payment and COD fees when known.
- Keep per-merchant fee configuration extensible.
- Snapshot financial values when an order is placed.
- Do not invent final commission percentages.
- Do not invent arbitrary merchant deductions.
- Do not implement automated merchant payouts yet.
- Do not treat product MRP as a configurable shipping surcharge.

For sandbox testing, allow explicitly configured demo
pricing policies and seeded test data.

Before enabling production checkout, require a validated
pricing configuration and relevant compliance checks.

The customer must not unexpectedly receive an additional
delivery charge after placing an order.

14. MERCHANT FULFILLMENT RESPONSIBILITY
============================================================

BUSINESS DECISION:

Approved merchants are contractually expected to fulfill
valid confirmed orders.

They must notify Gillu of planned unavailability.

Do not require an unnecessary "accept order" button
to establish the existence of a valid customer order.

Instead:

- Order becomes confirmed after the appropriate
  prepaid verification or COD validation.
- Merchant receives a notification.
- Merchant acknowledges or starts processing.
- Merchant packs the product.
- Merchant marks package ready.
- Shipping workflow begins.

Keep configurable acknowledgment and dispatch deadlines.

Add:
- Unacknowledged-order alerts
- Delayed-dispatch alerts
- Merchant availability settings
- Admin escalation

Do not implement financial penalties until the
merchant contract and penalty policy are finalized.

8. AWB is generated.
9. Label is generated.
10. Merchant requests pickup.
11. Courier collects parcel.
12. Shipment tracking is synchronized.
13. Shipment reaches delivered, failed, or returned state.
14. Customer and merchant dashboards update.

If Shiprocket succeeds but the HTTP response times out,
reconcile the external state before attempting to
create another shipment.

============================================================
30. CODE QUALITY STANDARDS
============================================================

- Use TypeScript strict typing.
- Avoid `any` unless carefully justified.
- Use runtime validation at system boundaries.
- Validate user inputs.
- Enforce authorization server-side.
- Keep handlers small.
- Keep domain logic separate from presentation.
- Keep external HTTP calls inside provider adapters.
- Use transactions for related database writes.
- Use idempotency for retries.
- Use structured errors.
- Avoid circular module dependencies.
- Avoid premature abstraction.
- Avoid duplicate code.
- Use descriptive naming.
- Add tests for important business rules.
- Write reversible migrations where feasible.
- Preserve existing working code.
- Do not perform destructive database operations without approval.
- Do not expose secrets in frontend bundles or logs.
- Do not bypass failing tests.

For each new feature, prefer:

1. Define expected behavior.
2. Write a focused failing test.
3. Implement the smallest working feature.
4. Verify tests pass.
5. Refactor only where needed.
6. Run relevant regression tests.
7. Document the change.

31. FINAL MVP ACCEPTANCE CRITERIA
============================================================

The project is considered complete when:

1. A merchant signs in using Google.

2. The merchant registers a shop.

3. An administrator approves the merchant.

4. The merchant adds products, images, and stock.

5. The products become visible on Gillu.

6. A customer signs in.

7. The customer adds products from multiple merchants.

8. The customer enters a valid delivery address.

9. The customer places a prepaid or COD order.

10. The application creates one parent order and separate
    merchant suborders.

11. Prepaid payment confirmation is verified through Cashfree.

12. Each merchant receives only their own order details.

13. A merchant can prepare the package.

14. Shiprocket registers and processes the shipment.

15. The merchant can retrieve the shipping label and AWB.

16. The merchant can request a courier pickup.

17. Customer and merchant can view shipment tracking.

18. The order progresses to delivery or an appropriate
    failure/return state.

19. The merchant dashboard shows accurate basic sales data.

20. The customer can leave an eligible verified review.

21. Automated tests cover the critical workflows.

22. The application can be deployed using Docker Compose.

All external provider verification must be accurately documented.
